## Two real defects the tests caught before this was ever run against real behavior

1. **Ordering bug**: the first implementation checked "is the host empty?" before "is the scheme trusted?" — for `file:///etc/passwd`, WHATWG URL parsing yields an empty hostname for the `file:` scheme specifically, so this order caused `file://` URLs to be rejected as `invalid_configuration` instead of the correct `policy_rejected` (an unsupported scheme should be the more fundamental rejection reason). Fixed by moving the scheme check first.
2. **A wrong assumption about URL parsing**: the test for "empty host" originally used `ws:///api/ws` (three slashes), assuming it would parse with an empty host. Verified empirically (`node -e`) that WHATWG URL parsing instead treats the string after `//` as the host — `ws:///api/ws` actually parses to host `"api"`, not empty — so this test case was testing the wrong thing entirely. Separately confirmed that for `ws:`/`wss:` (special schemes requiring a host), a genuinely empty host (`ws://`) causes the `URL` constructor to *throw*, which the existing `try`/`catch` already turns into `invalid_configuration`. Fixed by replacing the test with `ws://` and adding an explicit code comment noting the defensive (if currently unreachable) empty-hostname check.

## Endpoint trust requirements — status of each (Section 4)

- **Main-process ownership**: total — `connect()`/`disconnect()` remain zero-argument at every layer (contract, preload, main); `resolveTrustedEndpoint()` is called only inside `electron/hermesConnection.ts`; the `HermesTrustedEndpoint` type and the `hermesEndpoint` module name are structurally absent from every renderer-reachable file (`preload.ts`, `renderer.ts`, `shared-ipc-contract.ts`), proven by a dedicated test rather than only asserted.
- **No real configuration discovery**: `hermesEndpoint.ts` has zero imports — it cannot read `process.env`, a file, an OS setting, browser storage, a keychain, or a real server, because it has no way to reach any of them. Confirmed by a scan and by the module-boundary test asserting zero import statements.
- **Fail-closed design**: `resolveTrustedEndpoint()` has no fallback path of any kind — no localhost/LAN/remote default, no renderer-data inference, no token-shape inference, no workspace-path inference, no port guessing, no port scanning, no DNS/HTTP/TCP/WebSocket probing. It returns exactly one of three `unavailable` reasons or `trusted`; nothing else is possible.
- **Explicit endpoint model**: implemented as specified — `HermesTrustedEndpoint`'s two-arm discriminated union, with `endpointId`/`transport`/`hostPolicy`/`url: URL` on the trusted arm. `url` is a real `URL` object but is never renderer-facing (see reachability test above). No URL userinfo, query string, or fragment is ever permitted on a `trusted` result — all three are rejected unconditionally, regardless of `hostPolicy`, precisely because a query string is exactly where a token could otherwise be smuggled into an endpoint definition.
